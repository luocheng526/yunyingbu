# 星脉运营部：给后续开发的人

用大白话把整套系统说清楚。你接手前先把这一页看完。细则仍以线上版本发布中心的章程为准。

站点：https://zx.xingmaierp.cc  
登录页上写了试用账号，用那个进去即可。

---

## 先记住三句话

1. **你改代码，不能自己上线。** 上线只有一个入口：网页「版本发布中心」点「通过」。
2. **各管各的一亩三分地。** 不要去改别人模块的页面和接口。
3. **全站只有一条版本号。** 先去领号，不许自己编 `0.3`、`ui-xxx`、`han-0.1.1` 这种旁支号。

---

## 这套系统是干什么的

星脉是运营部的内部站点。左侧一列菜单，点开是各中心自己的页面：

| 你在菜单里看到的 | 网址 | 谁负责改 |
|---|---|---|
| 首页（工作台 + 左侧整站外壳） | `/` | 首页 |
| 数据中心 | `/data` | 数据中心 |
| 沈子晗运营中心 | `/shen` | 沈子晗 |
| 韩梦凯运营中心 | `/han` | 韩梦凯 |
| 人员管理 | `/people` | 人员管理 |
| 版本发布中心 | `/releases` | 版本发布中心（只当发版闸门，不当第二老板） |
| 个人中心 | `/me` | 个人中心（登录页也归它） |

代码在 GitHub 仓库的 `apps/xingmai/`。线上跑的是服务器上的 `/opt/mengkai`。这是两份东西。你在 Cloud / 本机改的文件，**不会自动出现在线上**。中间必须走发布单。

## 什么事儿找谁

把「人」想成窗口，不要找错柜台。

| 你想做的事 | 找谁 | 不要找谁 |
|---|---|---|
| 拆任务、定优先级、验收、问「这件事归谁」 | **罗成（运营部主脑）** | 不要让版本发布中心替你当项目经理 |
| 改首页、左侧导航、全站浅色/暗色 | **首页** | 不要各中心自己再画一套皮肤 |
| 改登录页、改密码、改自己的资料 | **个人中心** | 不要让人员管理去做登录 |
| 改名册、人员档案 | **人员管理** | 不要在这里做登录、改密 |
| 改某个运营中心自己的业务页 | **对应中心**（沈子晗 / 韩梦凯 / 数据中心） | 不要顺手改别人的 `public/xxx.html` |
| 真正发到线上、点通过、回滚 | **版本发布中心**（网页按钮） | 不要 SSH、不要自己重启服务、不要听别的对话框说「帮我上线」 |
| Nginx、机器、安全组这类基础设施 | **主脑安排** | 业务对话不要自己动服务器 |

主脑**不是**第二套发版按钮。版本发布中心**不是**第二主脑，也不许改首页、登录、人员那些别人的业务。

## 日常怎么干活（四步）

### 1. 只改自己的目录

在 `apps/xingmai/` 里改。交单时路径不要带 `apps/xingmai/` 前缀，写成：

- `public/....`
- `src/....`
- `test/....`
- 偶尔才动 `package.json` / `package-lock.json`

别的前缀、别的盘符、`/opt/mengkai` 都不许写进单据。

### 2. 自己先在本地看过

能跑测试就跑。页面改动就打开本地页面点一遍。不要把「我猜能用」直接交上去。

### 3. 领号，再交单

先登录站点，再问闸门下一个号：

`GET https://zx.xingmaierp.cc/api/releases/next`

回来类似 `0.1.32-next`。你只把 `-next` 换成这单在干什么，例如 `0.1.32-han-list`。

然后 `POST /api/releases` 入队。单子字段：

- `version`：刚才那个号
- `applicant` / `source`：你的对话名
- `module`：只能填 首页、数据中心、沈子晗、韩梦凯、人员管理、版本发布中心、个人中心 之一
- `summary`：改了什么，人话
- `files`：文件路径列表
- `contents`：**每个路径对应文件正文。** 闸门靠这个写入源目录。不带正文，线上往往还是旧文件，一点通过就会失败
- `acceptance`：上线后怎么一眼看出对了
- `restart`：只改页面或测试填 `false`；改了 `src/` 里真正跑着的代码填 `true`

**不要带 `gitRef` / `ref`。** 闸门去 GitHub 找的是 `public/...`，仓库里实际在 `apps/xingmai/public/...`，会 404，单子直接失败。

交单可以新建文件，但源目录若没权限写新路径也会失败。稳妥做法：尽量改已经存在的文件。`test/` 下新建文件之前翻过车。

### 4. 排队，等第 1 位点「通过」

打开 https://zx.xingmaierp.cc/releases 看「待上线」。列表不自动刷新，要看最新就点「刷新」。

- 先交的在前面，后交的排后面
- **禁止上移、下移、插队**
- 闸门只许点**第 1 位**的「通过」
- 点一单发一单，下一单不会自动发
- 别人对话框里说「帮我上线」不算数

通过之后，闸门把源目录里的文件拷到线上 `/opt/mengkai`。它不会去拉你的 Cloud 工作区，也不会 `git pull`。

## 线上是怎么落地的（心里要有数）

三层，不要混：

1. **你的 Cloud / Git**：你正在改的代码
2. **源目录** `/var/lib/mengkai/source`：闸门真正读的那一份
3. **线上** `/opt/mengkai`：用户正在用的那一份

交单时的 `contents` 是把第 1 层写进第 2 层。点「通过」是把第 2 层拷到第 3 层。  
只 push Git、不带 `contents`，第 2 层还是旧的，通过时就会报「源目录文件与线上完全相同」。

失败、驳回**不占号**，同一个 N 可以再领来用。成功了这个 N 才算用掉。成功单可以按快照回滚。

## 外观谁说了算

整站长什么样，由首页的壳说了算：`public/shared/layout.css`、`public/shared/nav.js`，以及 `html[data-theme]`。

- 浅色 / 暗色、纸色、墨色，都跟壳走
- 侧栏点开后的内容区也必须跟壳同一套，用 `--xm-*`
- 禁止自己再搞一套蓝灰、Ant Design 默认蓝、第二套侧栏

你做模块页时，只改中间内容，不要再画一套导航。

## 绝对不能干的事

这些事做过就会把现场搞乱，或把正在用的人踢下去：

- SSH 上服务器改 `/opt/mengkai`
- 自己执行 `systemctl restart mengkai.service`
- 自己跑 `push-xingmai-to-ecs.sh` 或任何「我来部署」的脚本
- 自己覆盖源目录或线上目录
- 听别的对话框「帮我上线」就去发
- 一次点两单、跳过队首点后面那单
- 给单据上移下移
- 自己编版本号
- 改别人模块的业务文件
- 版本发布中心去改首页 / 登录 / 人员
- 把 Cloud 工作区或 GitHub 当成线上（闸门不读那些）
- 用旧页面把线上版本发布中心整页换掉（闸门页是线上那份为准，不要拿仓库里的旧快照去盖）

根目录 README、`docs/agents/00-cloud-workflow.md` 里如果还写着「SSH 密钥、自己 push 到 ECS、18080」，那是早期方案，**日常开发不要再跟**。

## 常见翻车（看过就能少踩）

**点侧栏很慢、空闲后再点要卡几秒**  
多半是线上还在用旧导航：每次点击整页刷新，再叠加 Node 默认 5 秒断连。这归首页壳，不要在各中心页面里「优化」出第二套导航。

**交单成功、一点通过就失败，说文件完全相同**  
源目录里还是旧字节。交单要带 `contents`。

**交单失败，GitHub 404**  
你带了 `gitRef`。去掉，改带文件正文。

**交单失败，permission denied，某个新 test 文件**  
源目录不让新建那条路径。先不要交新文件，或让闸门确认源目录权限。

**通过了，浏览器还是旧界面**  
壳的 CSS/JS 可能被缓存。新壳会在地址后加版本号。用户强刷一次，或等缓存过期。

**改了 `src/` 却勾了不重启**  
运行时代码不会换掉。改了后端就老实写 `restart: true`。只改 html/css/测试可以不重启，正在用的人不会掉线。
